Dual-Agent Support

One conversation, two specialists, and visible context behind each reply.

The project separates API integration and billing questions. The original OpenAI CLI was expanded with a REST API, web interface, regression tests and a public demo on a self-hosted server.

What it does and why it exists

A visitor does not need separate channels for a technical problem and a billing question. A router passes the message to a specialist that uses documentation or billing tools. Shared context allows the issue to continue across messages.

The central engineering question is responsibility: when to retrieve evidence, when to call a tool, which fields are required, and how to handle missing knowledge. The public panel makes these decisions inspectable.

What actually runs publicly

The public version is rule-based and makes no LLM calls: it scores words and headings and returns documentation excerpts. Prices, cases and refunds are samples. It sends no email or money. OpenAI integration and vector retrieval remain in a separate CLI.

From a question to an inspectable reply

  1. 01 · Message

    The browser sends a question and session identifier to the REST API. The backend checks length, limits and conversation state.

  2. 02 · Select a specialist

    The demo router matches keywords and chooses TECH, BILLING, clarification for a mixed question, or an out-of-scope response.

  3. 03 · Documents or tools

    TECH searches local documentation sections. BILLING queries the catalog or collects the required fields for a sample refund.

  4. 04 · Reply and decision trail

    The interface shows the reply, route, executed tools and cited sources. The next message continues the same session.

For example, HTTP 401 selects TECH and cites the X-API-Key rule. A Pro pricing question switches to BILLING. A refund request starts collecting fields instead of creating an incomplete case.

Implementation and the skills the project demonstrates

REST API and conversation state

Endpoints for chat, documents, health and reset. A random identifier separates sessions, while the refund workflow retains required fields between turns.

HTTP contracts, state modeling and session isolation.

Routing and response sources

Separate technical and billing paths. The demo quotes real sections; no match produces a clarification. The separate CLI uses embeddings and an OpenAI model.

Separation of responsibilities, retrieval and explicit evidence.

Validated billing tools

Sample plan lookup, email and reason collection, a 14-day policy check when a date is provided, and a simulated case identifier. An existing case is not recreated in the same session.

Input validation, business rules and multi-turn workflows.

OpenAI integration fixes

Fixed assistant/tool sequencing, router-output validation, HTTP timeouts and embedding-cache invalidation after document changes. Local tests do not replace live API verification.

HTTP integration, tool-call protocols and regression testing.

Public demo bounds

30 turns per session, up to 300 active sessions and 120 messages per minute globally. State expires after 30 idle minutes, with cleanup every minute. No persistent conversation storage.

Data lifecycle and resource bounds.

Browser interface and deployment

The interface provides examples, loading and error states, and a decision trail. Docker Compose runs the service on Raspberry Pi as a non-root user; public HTTPS exposes the application.

Frontend/backend integration, Docker, Linux and diagnostics.

A two-minute walkthrough

Open the application without an account. Choose API authentication and expand the response source. Ask about Pro pricing. Then start a new conversation and select a refund: enter recruiter@example.com and I was charged twice. Inspect the follow-up questions, open_refund_case tool and DEMO identifier.

Use fictional data only. Also try an out-of-scope question and New conversation. The application interface is English; this portfolio case study is available in Polish and English.

Tests and actual limitations

19 automated tests

11 demo scenarios, 5 core regressions, 2 HTTP tests and a context test. The suite passed locally and in the Java 17 ARM64 image.

Workflow and isolation

Tests cover technical evidence, pricing, multi-turn refunds, separate sessions, reset, invalid dates and limits. Public HTTPS and desktop and mobile interfaces were checked.

Limited language understanding

The demo mainly uses English keywords. It is not an unrestricted AI chat or semantic RAG. State is lost on restart, and other visitors can exhaust the global request limit.

Integration verification boundaries

OpenAI fixes have local tests, but the paid API was not verified live during the audit. There is no real billing integration or model-quality guarantee. The server kernel does not enforce Docker RAM limits; the JVM has explicit memory bounds.
