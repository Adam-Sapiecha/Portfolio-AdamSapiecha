PERSONAL PROJECT · COMPUTER VISION / RGB-D

Posture Analysis System

Body geometry from RGB images and stereo depth.

I built an OAK-D camera pipeline, landmark detection and 3D calculations in Python. A separate web application processes user-supplied RGB-D data, saves capture history and exports reports. It runs on my Raspberry Pi 5.

What the application does

A landmark in an image is not enough to calculate a distance in centimetres. The program combines body landmarks with depth and camera calibration, converts them to XYZ, and calculates height differences, angles and asymmetries. Quality checks identify missing or unreliable input.

The project documents and inspects geometry. Saved images, landmarks and results make the calculations traceable. It is a research and educational prototype without clinical validation.

From an image to a result

  1. 01 · Capture

    OAK-D provides RGB and stereo depth. Alternatively, the web application accepts saved RGB, 16-bit depth in mm, and calibration.

  2. 02 · Landmarks

    The camera path uses MediaPipe to detect landmarks. The web application can import exported landmarks or let users mark four points manually.

  3. 03 · Geometry and quality

    A median depth sample around each landmark reduces outlier influence. Calibration provides XYZ coordinates, while a quality gate evaluates the input.

  4. 04 · Save and export

    Results, images and reports are stored in private SQLite history. Users can retrieve, download or delete their captures.

What a custom measurement requires

RGB and depth must represent the same scene, be aligned, and have matching dimensions. Depth must contain millimetres, and fx, fy, cx and cy must match the resolution. A photo or a colour depth visualisation alone is not sufficient.

What I implemented

Pipeline and detection

Mono camera, StereoDepth and RGB configuration, filtering profiles, and MediaPipe integration. The doctor, preview and report modes separate diagnostics, preview and capture.

pipeline.py · pose.py · app.py

Calculations and validation

Depth sampling around landmarks, outlier rejection, camera coordinates and metrics. A separate quality assessment retains errors and warnings.

reporting.py · config.py

Web application and persistent history

Flask handles RGB/depth/JSON uploads and actual processing. SQLite stores results and files, input hashes prevent duplicate captures, and PDF and JSON exports are available for download.

Access and deployment

Guest sessions have separate histories and limits. The backend checks ownership for every file. Docker Compose ARM64 runs the application on Pi with a persistent volume, a health check and bounded concurrency.

How I verified the application

Engine and API

32 tests passed locally and in a native ARM64 image. They cover geometry, invalid input, migrations, limits and session isolation.

Known geometry

With synthetic input ΔY = 18 px, Z = 2000 mm and fy = 600 px, the application calculated a 6 cm height difference. This calculation test is independent of the photo above.

Public HTTPS

Browser checks covered guest access, PNG/JSON upload, calculation, saved history, PDF export and denial of access from another session.

Data persistence

On Raspberry Pi I verified readback after container recreation, SQLite backup and startup against a restored database. Exported artifacts retained matching checksums.

Limitations and trial scope

The new OAK-D acquisition path has not yet been verified with a complete human measurement. MediaPipe does not directly locate C7, shoulder blades or PSIS. Public web tests used controlled inputs. Guests can process their own RGB-D: the limit is 3 captures / 20 MiB; history expires after 24 hours and is removed on the next API request.
